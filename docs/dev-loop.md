# 开发循环协议（dev-loop）

TokenMaster 的全自动开发流水线。每轮循环处理**一个**任务，状态全部落盘（TASKS.md / dev-log.md / git），任何中断后都能从板上续跑。

## 循环步骤（每个任务）

1. **领任务**：TASKS.md 中取最靠前、依赖全 `done` 的 `todo`，状态改 `doing`，commit 这次改动（或与任务完成提交合并）。
2. **红**：先写失败测试。测试只写在预定的缝上（缝 1 = 网关 HTTP 黑盒；缝 2 = provider 适配器 vs stub 上游；GUI 无自动化测试，走视觉自查）。断言行为（响应体/SSE 序列/错误码/账本记录），不断言内部结构；期望值来自 spec/参考实现的已知样例，不用实现反推。
3. **绿**：写**刚好**让测试通过的最小实现，不顺手加未来功能（垂直切片：一测一实现）。
4. **循环修复**：跑该任务相关测试文件；红→修→复测，直到绿。测试本身有错改测试，但先怀疑实现。
5. **自查（code review 内联版）**：过一遍清单——错误处理边界、并发安全（锁粒度/中毒锁）、命名与 CONTEXT.md 术语一致、无多余依赖、测试断言的确实是外部行为。
6. **关卡**：任务级 `cargo test -p <crate> <模块>` / `pnpm check`；里程碑级跑 TASKS.md 末尾的集成关卡（workspace 测试 + clippy + 前端构建）。
7. **文档**：docs/dev-log.md 追加一行（任务号/要点/测试数/提交号）；影响架构或术语的，更新 CONTEXT.md 或补 ADR。
8. **提交**：`类型(范围): 描述`（feat/fix/test/docs/chore），一任务至少一提交，保持可回退。
9. 回到 1。

## 并行规则

- 同一时间**至多一个**任务在改 Rust 核心 crates/、一个任务在改前端 src/（两者文件不相交时可并行，例如 GUI 移植与网关核心）。
- 并行时由主循环串行提交（避免两个执行体同时 git commit）。
- 任何共享文件（类型定义、CSS、TASKS.md）不允许两处同时修改。

## 中断恢复

一切状态在盘上：TASKS.md 的状态列就是断点；dev-log.md 是审计轨迹；git 历史是最终真相。恢复时：读 TASKS.md 找 `doing`（先验证其测试是否已绿）→ 继续；没有 `doing` 就领新任务。

## 质量红线

- 测试失败不提交；clippy 警告不新增（存量允许，修到零更好）。
- 凭据/密钥永不写进源码与测试字面量（Mimosa 约束）；测试用生成的随机密钥。
- 服务端出站 URL 仅 http/https；测试里的 stub 上游固定 127.0.0.1 随机端口。
- 界面文案不出现「示例/未接入」等制作说明。
